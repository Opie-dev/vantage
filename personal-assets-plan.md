# Vantage — adding personal investments (ASB · Tabung Haji · Gold)

**Owner:** syaafi · **Date:** 1 Sep 2026 · **Status:** Plan, not yet built
**Scope:** three MYR holdings that live outside moomoo — ASB, Tabung Haji and gold —
tracked in the same app, on the same dashboard, without touching the broker math.
**Reads with:** [commitments-and-income-plan.md](commitments-and-income-plan.md), which adds
salary, freelance income and what you owe. It assumes the tables below exist, reuses the
`SAVINGS` kind for EPF, and completes net worth by subtracting liabilities from it.

---

## 1. Why these do not go in `instruments`

The tempting shortcut is three rows in `instruments`: ASB at a fixed RM 1.00 price,
Tabung Haji the same, gold priced per gram. Every screen lights up for free.

It breaks four things, and three of them break silently.

| What breaks | How |
|---|---|
| **The wallet balance** | `cashBal()` subtracts every BUY from the MYR pocket. An ASB contribution is not money leaving your moomoo account, but that path would say it was. `brokerCash()` masks it today because a sync has run — so the bug sits dormant until the day one hasn't. |
| **The income run rate** | `monthlyIncomeRate()` averages the last 3 months. ASB pays **once a year**. One December distribution would triple the reported run rate for a quarter, then collapse it. |
| **Positions** | Eleven columns built for option-income ETFs — withholding tax, share-of-fund, declaration trend. ASB renders as a row of dashes with a permanent 0.00% P&L. |
| **Fund metrics** | `instrumentRows()` joins `fund_metrics` and `fund_distributions`, both fed only by moomoo's `get_market_snapshot`. Nothing would ever populate them for these three. |

So: **a parallel model, merged at the top.** New tables the broker code never reads,
new derivations in `calc.js`, and exactly one place where the two worlds are added
together — net worth. That keeps the warning at the top of `calc.js` true: the
financially load-bearing arithmetic is not being touched at all.

---

## 2. The three are not the same shape as each other

The second thing worth getting right. A single "other investments" table that treats
all three alike is nearly as wrong as putting them in `instruments`.

| | **ASB** | **Tabung Haji** | **Gold** |
|---|---|---|---|
| What you hold | Units, fixed at RM 1.00 | A ringgit balance | Grams |
| Price moves? | No | No | **Yes** |
| Unrealised P&L | Does not exist | Does not exist | The whole point |
| Return arrives as | Annual distribution, sen/unit | Annual profit, % (net of zakat) | Price appreciation only |
| Computed on | Mean of 12 monthly minima | Mean of 12 monthly minima | n/a |
| Credited | 1 January, as new units | March, into the balance | n/a |
| Holding cap | 300,000 units — but breachable | None | None |
| Realisable at the quoted price? | Yes, at RM 1.00 | Yes, at face | **No — there is a spread** |

Gold is a genuine *position*: quantity × price, average cost, unrealised gain. It maps
onto the existing mental model exactly.

ASB and Tabung Haji are not positions at all. They are **interest-bearing balances**.
No P&L, no market value, no cost basis in the trading sense. The only interesting
arithmetic is: what did I put in, what has it earned, at what effective rate, and what
will the next distribution be.

So the model needs **two kinds**, not one and not three:

- **`SAVINGS`** — a ringgit balance earning a periodic distribution on its minimum
  monthly balance. Covers ASB, Tabung Haji, and later ASN/ASM/ASB2 with no new code.
- **`COMMODITY`** — a quantity of a thing with a market price and a buy/sell spread.
  Covers gold, and silver if it ever comes up.

Two kinds behind a discriminator is the pattern `goals` already uses: a `kind` column
plus a `goals_shape_check` CHECK ensuring each kind carries the fields its math reads.
Mirroring it keeps the schema idiomatic and the failure mode loud.

## 3. Schema

Three new tables, two additive columns. All reversible; nothing existing changes
meaning.

### `assets` — identity

```sql
CREATE TABLE IF NOT EXISTS assets (
  id           INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  kind         TEXT NOT NULL,              -- SAVINGS | COMMODITY
  name         TEXT NOT NULL,              -- 'ASB', 'Tabung Haji', 'Public Gold 999'
  slug         TEXT NOT NULL UNIQUE,       -- 'asb' | 'tabung-haji' | 'gold' — stable UI key
  currency     TEXT NOT NULL DEFAULT 'MYR',
  institution  TEXT DEFAULT '',            -- 'ASNB', 'Lembaga Tabung Haji', 'Public Gold'
  account_ref  TEXT DEFAULT '',            -- last 4 of the account number, for your reference

  -- SAVINGS only
  unit_label   TEXT DEFAULT '',            -- 'units' for ASB; '' for TH, which is just ringgit
  unit_cap     DOUBLE PRECISION,           -- soft ceiling for the progress bar; NEVER a validation
  fiscal_year  TEXT DEFAULT '12-31',        -- MM-DD of the fund's year end (see §4.2)
  rate_basis   TEXT DEFAULT 'MIN_MONTHLY', -- MIN_MONTHLY | AVG_DAILY   (see §4.2)
  rate_quote   TEXT DEFAULT 'PERCENT',     -- PERCENT | SEN_PER_UNIT — display only
  last_rate    DOUBLE PRECISION,           -- most recent declared base rate
  last_bonus   DOUBLE PRECISION,           -- the discretionary top-up, kept apart (see §4.2)

  -- COMMODITY only
  unit         TEXT DEFAULT '',            -- canonical storage unit: 'g'
  quote_unit   TEXT DEFAULT 'g',           -- what the PROVIDER quotes in: g | ozt | coin
  purity       DOUBLE PRECISION,           -- 0.999, 0.916 … NULL when not applicable
  buyback_factor DOUBLE PRECISION,         -- the trade's own factor, NOT purity (see §4.3)

  sort_order   INTEGER NOT NULL DEFAULT 0,
  archived     BOOLEAN NOT NULL DEFAULT false,
  created_at   TEXT NOT NULL DEFAULT to_char(CURRENT_DATE,'YYYY-MM-DD')
);

ALTER TABLE assets DROP CONSTRAINT IF EXISTS assets_kind_check;
ALTER TABLE assets ADD CONSTRAINT assets_kind_check
  CHECK (kind IN ('SAVINGS','COMMODITY'));

-- Each kind must carry what its math reads, so no asset can exist in a state the
-- derivation cannot handle. The same guarantee goals_shape_check gives.
ALTER TABLE assets DROP CONSTRAINT IF EXISTS assets_shape_check;
ALTER TABLE assets ADD CONSTRAINT assets_shape_check CHECK (
     (kind = 'SAVINGS'   AND rate_basis IS NOT NULL)
  OR (kind = 'COMMODITY' AND unit <> '')
);
```

### `asset_entries` — the ledger

One table for every movement, as `transactions` is for the broker. Balances are
**never stored**; they are re-derived from this ledger on every render, which is the
invariant the whole app already runs on.

```sql
CREATE TABLE IF NOT EXISTS asset_entries (
  id        INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  asset_id  INTEGER NOT NULL REFERENCES assets(id),
  type      TEXT NOT NULL,              -- DEPOSIT | WITHDRAW | DISTRIBUTION | FEE
  date      TEXT NOT NULL,              -- YYYY-MM-DD, as every other date column
  amount    DOUBLE PRECISION NOT NULL,  -- always positive; `type` carries direction
  units     DOUBLE PRECISION,           -- grams for COMMODITY; NULL for SAVINGS
  note      TEXT DEFAULT '',
  source    TEXT NOT NULL DEFAULT 'manual',
  ext_id    TEXT UNIQUE                 -- unused today; the dedupe hook if a feed appears
);

ALTER TABLE asset_entries ADD CONSTRAINT asset_entries_type_check
  CHECK (type IN ('DEPOSIT','WITHDRAW','DISTRIBUTION','FEE'));
ALTER TABLE asset_entries ADD CONSTRAINT asset_entries_amount_check
  CHECK (amount >= 0);

CREATE INDEX IF NOT EXISTS asset_entries_lookup_idx ON asset_entries (asset_id, date DESC);
```

**Amount is always positive and `type` carries the sign** — how `cash_movements`
already works, and what `walletMovements()` reads. Signed amounts *plus* a type column
would be two sources of truth for one fact.

`units` is nullable rather than always populated because for a SAVINGS asset units and
ringgit are the same number by definition (RM 1.00 per unit); storing both invites them
to disagree. ASB units *are* `amount` — the UI just labels the column "units".

### `asset_prices` — the volatile half

```sql
CREATE TABLE IF NOT EXISTS asset_prices (
  asset_id   INTEGER PRIMARY KEY REFERENCES assets(id),
  buy_price  DOUBLE PRECISION,          -- what the dealer SELLS to you at, per quote_unit
  sell_price DOUBLE PRECISION NOT NULL, -- what the dealer BUYS BACK at — the valuation price
  spot_price DOUBLE PRECISION,          -- reference spot, so both sides can be shown against it
  fetched_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  source     TEXT NOT NULL DEFAULT 'manual'
);
```

Both retail sides are stored, and `spot_price` beside them, because the two move
independently — see §4.3. A schema that kept only a spread could not represent a dealer
whose buyback sits *below* spot, which is exactly what the widest-spread account does.

Split from `assets` for the same reason `prices` is split from `instruments`: identity
changes almost never, price changes daily, and `fetched_at` should describe only the
volatile half.

**Two prices, and the holding is valued at `sell_price`.** The one opinionated call in
the schema, and it matters more for Malaysian gold than for anything else here — §4.3.

### `snapshots` gains a column

```sql
ALTER TABLE snapshots ADD COLUMN IF NOT EXISTS assets_rm DOUBLE PRECISION NOT NULL DEFAULT 0;
```

The equity curve plots `value_rm + cash_rm`. Without this, adding assets makes today's
net worth jump against a history that never contained them — a step in the curve that
is purely an artefact of when the feature shipped.

The write paths stay cleanly separated. `snapshots.upsertToday()` is called by the
**sync worker** with the broker's own figures, and its `ON CONFLICT DO UPDATE` sets only
`value_rm` and `cash_rm`, leaving `assets_rm` alone. A second, server-side writer sets
`assets_rm` alone. Two writers, one column each, neither able to clobber the other — no
coordination needed, and a sync that knows nothing about assets still writes a correct
broker row.

### `goals` gains an asset target

```sql
ALTER TABLE goals ADD COLUMN IF NOT EXISTS asset_id INTEGER REFERENCES assets(id);
-- extend goals_kind_check  with 'ASSET_BALANCE'
-- extend goals_shape_check with:
--   (kind = 'ASSET_BALANCE' AND asset_id IS NOT NULL AND target_amount > 0)
```

One new kind covers the three goals worth having: *"RM 300,000 in ASB"*, *"RM 33,300 in
Tabung Haji"*, *"100 g of gold"* (a gram target expressed as its ringgit equivalent —
balance is the natural target for two of the three, so reusing `target_amount` beats a
second column).

`unit_cap` deserves one warning of its own: **it is a progress bar, never a constraint.**
ASB's 300,000-unit limit can legitimately be exceeded, because reinvested distributions and
inherited units are not new purchases. A CHECK on it would eventually reject a balance the
provider itself created.

## 4. The math — a new `── assets ──` section in `calc.js`

Every function pure, taking the whole state `S` first, exactly as the existing ones do.

### 4.1 Balance, cost and value

```
assetBalance(S, a)      SAVINGS:   Σ DEPOSIT + Σ DISTRIBUTION − Σ WITHDRAW − Σ FEE
                        COMMODITY: Σ units(DEPOSIT) − Σ units(WITHDRAW)

assetContributed(S, a)  Σ DEPOSIT − Σ WITHDRAW           your own money, net
assetEarned(S, a)       Σ DISTRIBUTION − Σ FEE           what it threw off

assetValueRM(S, a)      SAVINGS:   assetBalance
                        COMMODITY: grams × purity-adjusted sell_price
```

For a SAVINGS asset, `value − contributed === earned` identically. Worth asserting in a
test: if it ever fails, an entry has the wrong type.

`contributed` can legitimately go **negative** once withdrawals exceed deposits (put in
10k, earn 5k, take out 12k → contributed −2k, earned 5k, balance 3k). The arithmetic
stays right and total return is still `balance − contributed`. The UI must not treat
that as an error.

### 4.2 The distribution estimator — the reason this is worth building

ASB and Tabung Haji both compute their annual distribution on the **mean of the twelve
monthly minimum balances**, not the closing balance. This is confirmed in each provider's
own wording, and it is the single fact the whole feature rests on:

> ASNB, FY2025 FAQ — *"Total Monthly Minimum Balance for the Year ÷ 12 Months × Income
> Distribution Rate"*
>
> Tabung Haji — *"Average Minimum Monthly Savings Balance × 3.5% = (Total minimum savings
> balance for each month from January–December 2025 / Number of Months) × 3.5%"*

Note the shape precisely: the mean of the monthly *minima*, where a month's minimum is the
lowest the balance reaches between the 1st and the last day. Not average daily balance, not
closing balance.

That has a consequence most people holding them never see quantified: *a deposit made on the
2nd earns nothing for that entire month.*

```
minMonthlyBalances(S, a, year)   → 12 figures: the LOWEST balance held in each month,
                                    by walking the ledger forward day by day

projectedDistribution(S, a, year, rate = a.last_rate)
                                 → (Σ minimums / 12) × rate
```

Two things fall out that no spreadsheet gives you for free:

1. **What this year is on track to pay**, at last year's declared rate, updating every
   time you record a deposit.
2. **The cost of waiting.** Depositing RM 500 today rather than on the 1st of next
   month is worth `500 × rate × (months remaining / 12)` — a real ringgit figure the
   screen can state. Late in the year it is small. In January it is nearly the whole
   year's return on that money.

`rate_basis` stays a column even though both assets confirm as `MIN_MONTHLY`: it records
which rule an asset follows, so adding one that computes differently later costs a row
rather than a branch. Every projection is labelled an estimate at a rate that has not been
declared yet.

Four provider facts the arithmetic has to respect, each of which is easy to get subtly wrong:

- **ASB's headline rate is two numbers.** FY2025's 5.75 sen is 5.20 income distribution
  *plus* a 0.55 bonus — and the bonus comes from PNB rather than from the fund, is
  discretionary, and is not promised annually. When an *additional* bonus is declared it
  applies only to the **first 30,000 units**, which is a different base entirely. Hence
  `last_rate` and `last_bonus` as separate columns.
- **Tabung Haji's rate is already net of zakat.** TH pays it at fund level on depositors'
  behalf. Deducting zakat again would understate the return. (ASB is the other way round:
  its zakat facility charges 2.57% *of the distribution*, principal excluded.)
- **Credit dates differ, and one of them breaks naive compounding.** ASB reinvests on
  1 January, so its distribution lands in all twelve of the next year's minima. TH credits
  in **March** — recently 19 Mar 2026 for FY2025 — so it reaches only about ten of them.
  Compounding a TH balance as `balance *= 1 + rate` overstates the credit year by roughly
  a sixth.
- **Fiscal years are not all December.** ASB ends 31 December, but ASB 2 and ASM end
  31 March and ASB 3 Didik ends 30 June. `fiscal_year` exists so the twelve-month window is
  the fund's, not the calendar's.

Declared rates to seed with — ASB in sen per unit (income + bonus), TH as a percentage:

| FY | ASB | Tabung Haji |
|---|---|---|
| 2021 | 5.00 (4.25 + 0.75) | 3.10% |
| 2022 | 5.10 (3.35 + 1.25 + 0.50 on the first 30k) | 3.10% |
| 2023 | 5.25 (4.25 + 1.00) | 3.10% |
| 2024 | 5.75 (5.50 + 0.25) | 3.25% |
| 2025 | 5.75 (5.20 + 0.55) | 3.50% |

ASB declares in the second half of December (19 Dec for FY2025); TH declares on audited
results in February–April (18 Mar for FY2025). Neither date should be hardcoded.

### 4.3 Valuing gold honestly

Malaysian retail gold does not have one price. A dealer sells to you at one number and
buys back at a lower one, and the gap is not small — wide enough that a holding valued
at the sell-to-you price shows a paper gain that does not exist and would not survive
being realised.

So: **value at the buyback price**, show the spread as a named figure, and let the
detail card say what the position would actually realise today. The same instinct as
"the broker's balance is authoritative, the ledger is only history" and "declared is not
received" elsewhere in this app — the screen says the true thing even when a friendlier
number is available.

How wide the spread is depends entirely on the vehicle, and the range is enormous. These
are read from each provider's own page on 1 Sep 2026 — **not** from a rates aggregator, for
a reason given below:

| Vehicle | Round-trip spread |
|---|---|
| Public Bank GIA / eGIA | 3.83% |
| Maybank GIA | 3.86% |
| AmBank XAU | 4.32% (**quoted per troy ounce**, not per gram) |
| Bank Islam BIGA-i | 4.55% |
| BNM Kijang Emas | 3.96% at 1 oz · 5.78% at ½ oz · 7.48% at ¼ oz |
| Public Gold, 999.9 physical | 6.0% at 1 kg → 9.0% at 5 g |
| **CIMB eGIA** | **10.03%** |
| 916 jewellery | 12–20% |

**Do not use a rates aggregator for this.** Checked against the banks' own pages,
`rates.my` was exact on Public Bank, wrong on Bank Islam, and reported CIMB's spread as
**1.2% against an actual 10.03%** — off by nearly nine percentage points on the one vehicle
where it matters most.

**Store the two sides separately, not one "spread".** Most banks put their buy price 3–6%
*above* spot and their sell price roughly *at* spot. CIMB is the exception: it prices its
buyback ~5% **below** spot, and that is where its whole 10% comes from. A single spread
field cannot express the difference, and the difference is the entire point of valuing at
buyback.

**Purity is not applied at face value, and jewellery is penalised twice.** Two Malaysian
gold buyers' live pricing engines both use:

```
buyback per gram = (tael reference price ÷ 37.8) × FACTOR
```

with FACTOR of **0.900 for 916** — not 0.916. Also 0.985 for 999.9, 0.975 for 999, 0.820
for 835, and 0.700 for 750. So there is a haircut of roughly 1.5–2.5% below gold content
for the common marks, widening sharply below 18K (375 gets 0.290 against a 0.375 content).

On top of that, *upah* — the workmanship priced into a new piece, about +12% over gold
content — is never recovered. That is what turns a nominal spread into a real 12–20%
round trip, and it is worth a line on the card for any 916 holding, because the purity
arithmetic on its own looks far more reassuring than the outcome.

Entry is in **grams, canonically** — the form offers g / oz t / kg and converts on the way
in. One troy ounce is exactly 31.1034768 g.

**Mayam is display-only if offered at all.** Malaysian sources put it at **3.33–3.37 g**
and nothing supports the 3.75 g figure that is easy to reach for (that is the Chinese
*chee*). The tael is the live trade unit at **37.7994 g**, though shops divide by **37.8** —
replicate the rounding if you ever want to reproduce a shop's quote exactly. Grams are
canonical; a mayam conversion, if wanted, is a configurable constant on the display layer
with the ambiguity stated, never a factor inside a valuation.

One more per-vehicle field falls out of the table above: **`quote_unit`**. AmBank quotes
per troy ounce, Kijang Emas per coin, everyone else per gram.

### 4.4 Net worth — the one place the two worlds meet

```
netWorth(S) → {
  brokerRM,     // portfolio(S).totalRM — unchanged, untouched
  assetsRM,     // Σ assetValueRM
  bySlug,       // { asb, 'tabung-haji', gold } for the split bar
  totalRM,
}
```

That is the entire integration surface. `portfolio()` keeps its current meaning and
signature, every existing caller keeps working, and the broker figures on the Dashboard
keep saying exactly what they have always said.

### 4.5 What deliberately does NOT change

| Function | Why it stays broker-only |
|---|---|
| `income()` | Feeds the income-focus Dashboard and the income goals, all built around weekly ETF distributions. |
| `monthlyIncomeRate()` · `averagePayment()` | 3-month and 3-payment averages. An annual distribution is meaningless in both. |
| `incomeOutlook()` · the Calendar | Driven by declared ex-dates and learned settlement lag. ASB declares once, in December, with no ex-date. |
| `positions()` · `cashBal()` · `brokerCash()` | The load-bearing block. Nothing here reads an asset. |

Asset distributions get their own annual framing (`assetIncomeYear()`), and anywhere a
combined "income from everything" figure appears it is an explicit, labelled sum — never
a silent merge into a number that used to mean something narrower.

**Deferred on purpose:** letting `INCOME_TOTAL` / `INCOME_YEAR` goals count asset
distributions. Reasonable to want ("RM 12,000 a year across everything") and the goal
shape already supports it — but `INCOME_MONTHLY` and `INCOME_PER_PAYMENT` must never
include them, so it is a per-kind rule needing its own UI explanation. Phase 5.

## 5. Prices for gold

No OpenD path exists for gold, and — checked directly against the API — **Yahoo has no
MYR gold symbol at all**: `XAUMYR=X`, `XAUUSD=X` and `XAU=X` all return *"No data found,
symbol may be delisted"*. `^XAU` exists but is the PHLX gold/silver *mining-equity* index,
which would be a quietly wrong number rather than a missing one.

Four sources, in order of preference:

0. **The provider's own page**, for anything you actually hold. Public Bank, CIMB, AmBank
   and Bank Islam all serve clean HTML to a plain `curl`; Maybank sits behind Akamai and
   does not. This is the only way to get a *retail* price, and no spot feed substitutes for
   it — see the aggregator warning in §4.3.

1. **Bank Negara's Kijang Emas open API** — no key, no auth, and the only free feed that
   returns a genuine **two-sided** quote:

   ```
   GET https://api.bnm.gov.my/public/kijang-emas
   Accept: application/vnd.BNM.API.v1+json
   → {"data":{"effective_date":"2026-08-26",
       "one_oz":{"buying":19150,"selling":19950}, …}}
   ```

   Prices are MYR per coin; divide by 31.1034768 for per-gram. It publishes on business
   days and **lags** — the feed was four business days stale when checked — so
   `fetched_at` has to be shown, not assumed fresh.

2. **Manual entry**, which stays first-class rather than a fallback. Every bank and dealer
   publishes their own buy and sell price daily, and only *your* dealer's buyback is the
   price you can actually realise. Typing two numbers takes ten seconds and beats any feed
   for accuracy.

3. **True spot**, for the reference line the gold card shows against the dealer price:
   `api.gold-api.com/price/XAU` gives USD/oz with no key, and BNM's own
   `/exchange-rate/usd?session=1200&quote=rm` gives the authoritative USD/MYR middle rate.
   Divide by 31.1034768.

4. **`GC=F` as the fallback only**, flagged as futures-derived: COMEX futures × `USDMYR=X`
   ÷ 31.1034768. The active contract carries contango measured at **+1.20%** over spot on
   the day checked, it jumps discontinuously at each roll (so a historical series shows
   phantom gaps), and its quote is ~10 minutes delayed and timestamped in a different
   timezone from the FX leg. Store the basis against source (3) as a diagnostic so drift is
   visible rather than silent.

`refreshFromYahoo()` extends naturally for (4) — it already loops, reports per-item success
and never lets one failure abandon the rest. (1) and (3) are new fetches alongside it under
the same contract.

**Freshness is per endpoint, not per host.** When checked, BNM's FX endpoint served that
day's rate while its Kijang Emas endpoint sat six days stale, September returned an empty
array, and BNM's own page said the rate display was temporarily unavailable — with no
announcement explaining it. Meanwhile a third-party site claiming to mirror that API was
publishing a current-dated figure that does not exist in it. So: check `effective_date` on
every response and show it, and never trust a mirror.

from, and this data is tiny — three assets and a few hundred entries. A second fetch
would buy nothing and cost a second loading state.

## 7. UI

### 7.1 A new screen: **Assets**

Ninth entry on the rail (`LandmarkIcon` is taken by Instruments — `CoinsIcon` or
`PiggyBankIcon`).

- **A total strip** — combined value, total contributed, total earned, blended return.
- **One card per asset**, laid out by kind:
  - *SAVINGS card* — balance as the headline, contributed / earned beneath, a cap
    progress bar when `unit_cap` is set, the effective return achieved so far, and the
    **projected distribution** panel: this year's minimum-monthly-balance average, the
    rate it is priced at, the resulting figure, and the deposit-timing nudge. Marked as
    an estimate throughout.
  - *COMMODITY card* — grams held, average cost per gram, current buyback price, market
    value, unrealised P&L, and the spread stated plainly: "you would realise RM X today;
    the dealer's sell price is RM Y".
- **The entry ledger** beneath, filterable per asset, in the same table idiom as
  Wallet's movement list.

### 7.2 Dashboard

One addition, above the existing cards and deliberately not merged into them: a
**net worth strip** — the total, and a segmented bar splitting broker / ASB / Tabung Haji
/ gold in the existing `--chart-*` slot colours.

Everything currently on the Dashboard keeps meaning what it means today. The income hero
is still ETF income; the P&L basis toggle still governs broker P&L alone. The strip is
additive context, not a redefinition — which is also what keeps it a small, low-risk diff
to a 1,600-line screen.

### 7.3 Allocation donut

Assets join as slices. A real improvement rather than a courtesy: the donut currently
shows three US ETFs and a cash sliver, reading as a wildly concentrated portfolio. With
ASB and gold in it, it finally shows the actual shape of the money.

### 7.4 Goals

`ASSET_BALANCE` goals render in the existing goal-card layout — progress bar, remaining,
and months-to-target from `monthly_budget`, which for ASB is the single most useful
projection in the app: *"RM 500/month reaches the cap in N years."*

### 7.5 Wallet, History, Calendar

**Untouched in phase 1.** An ASB contribution is not a moomoo cash movement and must
never reach the wallet balance. If a combined "everything that moved" ledger is wanted
later it is a presentation-layer union in History with a source column — not a change to
`cash_movements`.

## 8. Phases

1. **Schema + API.** Three migrations, the model/service/controller/route stack, three
   new keys on `/api/state`. Verifiable with curl before any UI exists.
2. **Assets screen + calc.** Balance / contributed / earned / value, the ledger, both
   card kinds, manual gold price. At the end of this phase the feature is usable.
3. **The estimator.** Minimum-monthly-balance walk, projected distribution, the
   deposit-timing nudge. The part with real analytical value, and the part worth getting
   right rather than fast.
4. **Integration.** Net-worth strip, donut slices, `assets_rm` snapshots plus a backfill,
   `ASSET_BALANCE` goals, derived gold spot as a reference price.
5. **Optional.** Asset income inside the annual goal kinds; a combined History view;
   zakat-on-gold surfacing if wanted.

Phases 1–2 are the minimum that beats a spreadsheet. Phase 3 is why you would build this
rather than keep the spreadsheet.

## 9. What is settled, and what is not

The distribution basis — the one thing this feature could not be built without — is now
**confirmed from both providers' own published wording**, quoted in §4.2. That was the
largest risk and it is closed.

### Genuinely unresolved, and worth deciding before phase 2

- **Realised gain on a partial commodity sale.** `assetContributed()` as specified is
  Σ DEPOSIT − Σ WITHDRAW in *money*, which is not the same as cost basis once you sell part
  of a holding at a price above cost: selling 5 g of a 26 g position removes 5 × avg from
  the basis but a different figure from the cash total, and the difference is realised gain
  that lands in neither `contributed` nor `earned`. `positions()` already solves this for
  the broker (a SELL removes at the running average, leaving it unchanged) — the asset
  version should do the same and carry a separate realised figure. Not modelled above.
- **ASB after a mid-year full exit.** ASNB states eligibility as holding at least one unit
  at year end, but its own worked FY2023 example pays RM 177.09 to an investor who redeemed
  everything in May. The two cannot both be right. Treat a full mid-year exit as undefined
  rather than guessing.
- **Which gold price a provider is quoting.** Maybank's rates page is Akamai-blocked to
  automated fetches, so its figures could not be read from the source; the UOB account's
  minimum is variously reported as 5 g, 20 g and 1 kg; and Public Gold publishes neither a
  1 g bar spread nor a GAP buyback. Any of these needs confirming against a statement
  before it is trusted in a valuation.

- **Malaysia introduced a 10% import duty on gold bars on 8 June 2026**, its first, and the
  scope is genuinely disputed: early reporting says LBMA-standard 99.99% bars, while a later
  and more specific account says *stamped/minted* retail bars are dutiable and *cast* bars
  are exempt — close to opposite in retail effect. Jewellery is exempt under both readings.
  It may be part of why physical currently sits 6–8% over spot. Worth knowing before reading
  a dealer premium as a dealer's greed.

### Standing risks

- **Snapshot backfill.** SAVINGS balances reconstruct exactly from the ledger (a pure
  running sum). Gold cannot — there is no historical RM/g series here, so pre-today gold is
  carried at cost. Defensible, and it must be stated on the chart rather than smoothed over,
  exactly as `backfill_equity.py` already declares its constant-FX approximation on every run.
- **Manual entry is the only input.** No API exists for any of the three balances. The
  ledger is only as current as the last time you typed into it, so each card should show how
  stale it is — the app already does this for prices and for last sync.
- **The gold spread is a live number**, and the BNM feed lags by days. A stale `sell_price`
  misstates the position by however much gold has moved since. Same staleness treatment as
  `fetched_at` on fund metrics.
- **Rates and caps are policy, not physics.** ASB's cap rose from RM 200k to RM 300k; TH
  dropped its second "Hibah Haji" tier after FY2017 and stale figures for it still circulate
  online; the hajj payment became means-tested in 2022 (RM 15,000 / 23,500 / 33,300 against a
  RM 33,300 cost, with RM 15,000 now the threshold for an offer letter). All editable
  columns, none of them constants in the code.
- **Everything price-shaped here is a snapshot** of 1 September 2026 and was stale the
  moment it was written.
